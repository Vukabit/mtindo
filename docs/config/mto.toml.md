# `mto.toml` settings

mto's own settings, which only `mto.toml` and `.mto.toml` may hold; the standard
formatter would not understand them. Besides these, an `mto.toml` may set
`root = true`, so that the search upwards for more `mto.toml` files stops at it,
and any of the formatting settings in [rustfmt.toml.md](rustfmt.toml.md).

Generated by `cargo xtask docs config` from mto's settings table;
[README.md](README.md) explains how mto finds its settings.

## Settings

### `blank_lines_between_blocks`

The number of blank lines placed between items. Imports of the same group and
`mod name;` declarations stay on consecutive lines. It is kept within the
standard formatter's `blank_lines_lower_bound` and `blank_lines_upper_bound` (0
and 1 by default), with a warning, so that the standard formatter leaves the
result alone; imports and declarations get the lower bound.

*   Type: a whole number, zero or more.
*   Default: `1`, in every style edition.
*   In mto: supported.

### `group_impls`

Rank each impl block as the struct, enum or trait it is for and place it right
after that item, instead of in the `ImplBlock` group of `type_order`.

*   Type: `true` or `false`.
*   Default: `true`, in every style edition.
*   In mto: supported.

### `ignore_dirs`

Folder names skipped when mto walks a directory. A folder is skipped wherever it
appears; setting this list replaces the default list.

*   Type: an array of strings.
*   Default: `[".git", "target", "node_modules", "vendor", "dist", ".venv"]`, in
    every style edition.
*   In mto: supported.

### `impl_method_order`

The order of the functions inside an impl of a trait declared in the same file.
Only the functions trade places; other items and blank lines stay where they
are. A trait declared under the same name twice in the file is skipped. The
standard formatter's `reorder_impl_items` is honored as well, as the standard
formatter applies it.

*   Type: one of the values below, as a string.
*   Default: `"written"`, in every style edition.
*   In mto: supported.
*   Values:
    *   `written`: Functions in impl blocks keep the order they were written in.
    *   `trait`: In an impl of a trait declared in the same file, the functions
        follow the order of the trait's declaration; functions the trait does
        not declare come after them.

### `import_grouping`

Separate `use` declarations into three groups, in this order, with a blank line
between groups: the standard library (`std`, `core`, `alloc`), external crates,
and local paths (`crate`, `self`, `super`). Only applies when `sort_imports` is
on.

*   Type: `true` or `false`.
*   Default: `true`, in every style edition.
*   In mto: supported.

### `import_sort`

Imports are sorted exactly as the standard formatter sorts them, so the standard
formatter leaves them alone. This picks which of the standard formatter's two
orders to use when it should differ from the style edition in effect.

*   Type: one of the values below, as a string.
*   Default: `"style_edition"`, in every style edition.
*   In mto: supported.
*   Values:
    *   `style_edition`: Sort imports as the standard formatter does for the
        style edition in effect.
    *   `2015`: the standard formatter's order before style edition 2024:
        snake_case, then CamelCase, then UPPER_SNAKE_CASE, each by bytes, so
        `a10` comes before `a2`.
    *   `2024`: Version sorting, as from style edition 2024: numbers by value,
        so `u8` comes before `u16`, and uppercase before lowercase.

### `layout`

Turns layout on for the files this mto.toml applies to. Off by default, so mto
changes nothing until a project opts in; `mto init` writes an mto.toml with it
on. An mto.toml without it may still override the standard formatter's settings.

*   Type: `true` or `false`.
*   Default: `false`, in every style edition.
*   In mto: supported.

### `format`

Turns formatting on for the files this mto.toml applies to, beside or without
`layout`. A preview. A `let` with an initializer, or an expression statement,
whose expression is a call, method chain (`?` and `.await` too), struct literal,
array, tuple, macro call or `return` is laid out anew (a macro's arguments in
parentheses as a call's, in brackets as an array's, when they read as
expressions; in braces left as written after `name! `), a `let`'s pattern with
it, its lines broken and joined as the Rust style does within `max_width` and
the widths `use_small_heuristics` sets (unless it holds a comment, block or
macro, a closure that would break, or a type or generic arguments that would
have to break); any other statement is put on one line when it fits there with
everything in it within its width; so is a `use` declaration, its lists laid out
as `imports_layout` says, unless it holds a comment, an attribute or a list of
one item, which the Rust style would rewrite; and so is an attribute of a file,
body, item, statement, field or variant whose arguments are names and values,
within `attr_fn_like_width` (`#[derive(...)]` its own way). Items, attributes
and statements start lines of their own, as do the tail and closing brace of a
block holding a statement and of a function's body. An item's header
(`pub fn name<T>(a: T) -> R {`, `impl<T> Trait for Type {`, `pub struct Name {`)
is joined onto one line when it fits (and so is a type alias, const or static),
else a function's parameters are put one per line, unless it holds a comment, a
`where` clause, trait bounds or generics that would break. A struct's fields and
an enum's variants are one per line, each on one line with its comma (a
struct-like variant within `struct_variant_width`, else one field per line).
Runs of `use` items and of `mod name;` declarations (no blank line between) are
sorted as the Rust style sorts them, unless `reorder_imports` or
`reorder_modules` is off or the run holds a comment. Other lines are not broken
or joined yet. The lines that start items, statements, fields, variants, match
arms and list elements are indented one level past the line their block or list
belongs to (match arms not, with `match_arm_indent = false`), and closing
delimiters at that line's indentation; the lines that continue them move along
with them. Within a line, tokens are spaced as the Rust style spaces them
(`a + b`, `f(x)`, `a::b`, `x: T`), honoring `spaces_around_ranges`,
`space_before_colon`, `space_after_colon` and `type_punctuation_density`; a pair
no rule covers keeps its spacing. Trailing whitespace is trimmed after code and
line comments, blank lines are kept within `blank_lines_upper_bound` and dropped
at the start and end of a container (a module body keeps its first, an extern
block both), lines end as `newline_style` says and the file ends with one line
break, honoring `tab_spaces` and `hard_tabs`. As the standard formatter does,
mto leaves as written macro bodies, anything marked `#[rustfmt::skip]`,
`// mto: off` regions, `macro_rules!` definitions, attributes whose arguments
are not names, `name = literal` or lists of them, a statement or item with a
line longer than `max_width` (counting the lines of closures, arguments and
match arms inside it), a statement with a comment between a binary operator's
operands, and files that `disable_all_formatting` or
`format_generated_files = false` leave alone. Every change is checked to keep
the program's tokens and comments.

*   Type: `true` or `false`.
*   Default: `false`, in every style edition.
*   In mto: partial. Indentation, spacing within lines, blank lines, trailing
    whitespace and line endings; no line breaking yet.

### `name_sort`

How `sort_alphabetically` compares names. Imports and modules are not affected:
they are always sorted exactly as the standard formatter sorts them.

*   Type: one of the values below, as a string.
*   Default: `"version"`, in every style edition.
*   In mto: supported.
*   Values:
    *   `version`: The Rust style guide's version sorting: numbers by value
        (`u8` before `u16`), underscores first, uppercase before lowercase.
    *   `bytes`: Byte by byte, so `a10` comes before `a2`.
    *   `case_insensitive`: Version sorting with case ignored (`alpha`, `Beta`,
        `gamma`), case deciding only between otherwise equal names.

### `sort_alphabetically`

Within each kind of `type_order`, items are ordered by `visibility_order`, then
by name (see `name_sort`) when this is on. When off, items of the same kind and
visibility keep their original order.

*   Type: `true` or `false`.
*   Default: `true`, in every style edition.
*   In mto: supported.

### `sort_imports`

Sort `use` declarations: by group when `import_grouping` is on, then `self`,
`super` and `crate` paths ahead of the rest, then by path. When off, imports
keep the order they were written in; pair it with the standard formatter's
`reorder_imports = false`, or the standard formatter sorts them.

*   Type: `true` or `false`.
*   Default: `true`, in every style edition.
*   In mto: supported.

### `test_module`

Where `#[cfg(test)]` modules go: last in the file, or kept where they are.

*   Type: one of the values below, as a string.
*   Default: `"last"`, in every style edition.
*   In mto: supported.
*   Values:
    *   `last`: At the end of the file.
    *   `in_place`: Where it was written: it keeps its place, like a pinned
        item.

### `trait_impl_order`

Trait impls for these traits come right after the type's own impls, in this
order, for example `["Default", "Clone", "Debug", "Display"]`. A trait is
matched by its name without its path, so `fmt::Display` matches `Display`. Other
trait impls follow, as `trait_impl_sort` says.

*   Type: an array of strings.
*   Default: `[]`, in every style edition.
*   In mto: supported.

### `trait_impl_sort`

The impls of one type go in this order: the type's own impls, as written; the
trait impls listed in `trait_impl_order`; then the other trait impls, by trait
name or as written.

*   Type: one of the values below, as a string.
*   Default: `"name"`, in every style edition.
*   In mto: supported.
*   Values:
    *   `name`: By trait name, in `name_sort` order.
    *   `original`: As written.

### `type_order`

The order in which kinds of items appear in a file, top to bottom. Kinds left
out of the list go after the listed ones, in their default order. `#[cfg(test)]`
modules go where `test_module` says. `extern crate` items and item macro calls
(such as `include!`) are not kinds here: they never move, because moving them
can change what the code means.

*   Type: an array of the values below, each at most once.
*   Default: `["ModDecl", "UseDecl", "MacroDecl", "MacroDef", "ConstDecl",
    "StaticDecl", "TypeAlias", "TraitDecl", "EnumDecl", "StructDecl", "Union",
    "ImplBlock", "ExternBlock", "FnDecl", "Unknown"]`, in every style edition.
*   In mto: supported.
*   Values:
    *   `ModDecl`: Module declarations: `mod name;` and `mod name { ... }`.
    *   `UseDecl`: Imports: `use` declarations.
    *   `MacroDecl`: `macro_rules!` definitions.
    *   `MacroDef`: `macro` definitions (declarative macros 2.0).
    *   `ConstDecl`: Constants: `const`.
    *   `StaticDecl`: Statics: `static`.
    *   `TypeAlias`: Type aliases: `type Name = ...;`.
    *   `TraitDecl`: Traits, including trait aliases.
    *   `EnumDecl`: Enums.
    *   `StructDecl`: Structs.
    *   `Union`: Unions.
    *   `ImplBlock`: Impl blocks.
    *   `ExternBlock`: `extern` blocks: `extern "C" { ... }`.
    *   `FnDecl`: Functions.
    *   `Unknown`: Items of no other kind, such as `reuse`.

### `visibility_order`

Within each kind of `type_order`, items are ordered by visibility in this order
before they are sorted by name. Visibilities left out go last. Modules ignore
it, as the standard formatter does.

*   Type: an array of the values below, each at most once.
*   Default: `["Pub", "PubCrate", "PubIn", "PubSuper", "Private"]`, in every
    style edition.
*   In mto: supported.
*   Values:
    *   `Pub`: `pub`.
    *   `PubCrate`: `pub(crate)`, and `pub(in crate)`, which the standard
        formatter writes so.
    *   `PubIn`: `pub(in path)` for any other path.
    *   `PubSuper`: `pub(super)`, and `pub(in super)`.
    *   `Private`: No visibility, `pub(self)` or `pub(in self)`.
