## 1 Question

Is there any input that makes mto crash, run out of memory, hang, write code
that means something else, or write output that a second run would change?
Tests cover the inputs someone thought of; fuzzing searches for the rest by
generating inputs, guided by which code they reach. Its results are the
failures it finds, the inputs kept so they stay fixed, and how much of mto
the search reaches.

## 2 Method

Each fuzz target is a libFuzzer harness under fuzz/fuzz_targets/ that feeds
generated bytes to one part of mto and checks a property:

- `lexer`: in every edition, no panic, and the tokens are never empty, end
  on character boundaries and cover the input exactly.
- `parser`: in every edition, no panic, and the tree prints back the input
  byte for byte.
- `layout`: when layout arranges a file, the layout meaning check is clean
  on the result and arranging it again changes nothing.
- `format`: formatting keeps the meaning check clean and settles in one run,
  whatever the input and settings (the first bytes pick the settings).
- `comments`: comments inserted between tokens all survive layout, which
  never writes what the verifier would refuse.
- `generated`: source built from the bytes so that it always parses, run
  through layout, formatting and both, each keeping its meaning and settling
  in one run.
- `verify`: the verifier raises no false alarm: a file checked against
  itself, or against its own items moved around, is clean.
- `toml`: the configuration reader never panics, and every error points
  inside the document.

`cargo xtask fuzz run TARGET` runs one target for a while (60 seconds by
default) with the address sanitizer and libFuzzer's 2048 MB memory limit.
Every input libFuzzer saves (a crash, running out of memory, a timeout, a
slow unit or a leak) is filed as an incident: a signature built from the
kind, the target, the panic's location and the failing check's message
decides whether it is new or another occurrence of a known one. An incident
can be replayed, shrunk to a smaller input that still fails, and, once
fixed, promoted: its input is kept under tests/fuzz_regressions/TARGET/ and
runs through the target's checks in every test run from then on.

`cargo xtask test --group fuzz` runs every target for `--fuzz-time` seconds
(10 by default). `cargo xtask fuzz diff` fuzzes differentially against the
standard formatter, on corpus files scrambled with a fresh seed and on
generated source, and files every way the two disagree as a `mismatch`
incident; mismatches measure compatibility and never fail the suite.
`cargo xtask fuzz coverage` measures which lines of src/ the targets'
corpora reach.

The tracked record of fuzzing is the set of kept inputs: their count per
target is this paper's checked data. Incidents, run speeds and coverage are
kept on the machine that ran them.

## 4 Threats to validity

- **No finding is not no bug.** Fuzzing finds what its inputs reach in the
  time given. The coverage figures say how much of src/ the corpora reach;
  code they do not reach is untested by fuzzing.
- **Short runs in the suite.** The fuzz group runs each target for seconds,
  enough to catch a regression in reached code, not to explore. Longer runs
  are made by hand, and their length is not recorded in a tracked file.
- **Runs are not repeatable by seed.** libFuzzer picks a seed per run and
  the runner does not keep it; a failure is reproduced from its saved input
  instead, which every incident keeps.
- **The sanitizer changes speed and memory.** Inputs per second and peak
  memory are measured with the address sanitizer on, which costs both;
  they compare runs with each other, not with mto as shipped.
- **Kept inputs count fixed bugs, not quality.** A target with no kept
  inputs either never failed or failed only before inputs were kept. The
  count shows how much the regression suite holds, not how robust a part
  is.

## 5 Reproduction

Fuzzing needs a nightly Rust toolchain and `cargo-fuzz`.

```bash
# Fuzz one target for five minutes, then file what it found
cargo xtask fuzz run format --time 300
# Every target, briefly, as the suite does
cargo xtask test --group fuzz
# The incidents; replay, shrink or keep one as a regression test
cargo xtask incidents list
cargo xtask incidents replay ID
cargo xtask incidents minimize ID
cargo xtask incidents promote ID
# Differential fuzzing against the standard formatter
cargo xtask fuzz diff --time 120
# What the corpora reach
cargo xtask fuzz coverage
# Regenerate this page
cargo xtask docs metrics
```
